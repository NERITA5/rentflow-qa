# BUG-001: Landlord with no existing tenants can never create their first lease

**Found:** During functional testing of the lease-creation flow
**Environment:** Local dev (localhost:3000), Chrome, RentFlow
**Status:** Fixed and verified

## Summary

While testing the "New Lease" flow as a landlord, I hit a dead end: the tenant dropdown was
completely empty, with no way to proceed. Digging into it, this turned out to be a real
chicken-and-egg bug in how the app decides which tenants a landlord is allowed to see.

## Steps to reproduce

1. Log in as `landlord@rentflow.dev` — a landlord account that owns two properties
   (Downtown Business Lofts, Harbourview Residences) but has never leased to anyone yet
2. Go to Leases → New Lease
3. Click the Tenant dropdown

**Expected:** Some list of tenants I could choose from, so I can create a lease.

**Actual:** Nothing. The dropdown is empty every single time, no matter what I do.

## Why this matters

This isn't an edge case — it's the *normal* state for any brand-new landlord account. If this
shipped as-is, literally no new landlord could ever lease to a first tenant. That's a core
workflow completely broken, not a minor annoyance.

**Severity:** High | **Priority:** High | **Reproducibility:** 100%, every time

## Root cause

I traced it to the `GET /api/tenants` endpoint, which powers that dropdown. It only returns
tenants who are *already* connected to the landlord through an existing lease. Which is exactly
the problem — a landlord with zero leases can never have any "connected" tenants, so the list
is permanently empty. There was no other path in the entire app to reach a tenant for the first
time. A closed loop with no way in.

## The fix

Added a second mode to that same endpoint (`?scope=available`) that instead returns any tenant
who currently has no active lease — regardless of who they were previously connected to. Pointed
the New Lease form at this new mode instead of the default one.

## A second bug I found while re-testing the fix

After deploying the fix, I re-tested and the dropdown was *still* empty. Turned out the API
response had no `Cache-Control` header, so the browser had cached my very first (empty) request
and kept serving that stale response even after the fix was live. I only caught this by hitting
the endpoint directly with a cache-busting query string and comparing the raw JSON before and
after — the actual code was correct the whole time, my browser just wasn't asking for a fresh
answer. Added explicit `Cache-Control: no-store` headers so this can't happen again.

**Lesson for myself:** when re-testing a fix, always force a genuinely fresh request (hard
refresh, incognito, or a cache-busting param) — otherwise you can spend a long time debugging a
"bug" that's actually just a stale cache showing you yesterday's answer.

## How I verified it was actually fixed

Not just "clicked around and it looked fine" — I hit the raw API directly and compared:
- Before the fix: `{"data":[],...,"total":0}`
- After the fix: 5 real tenants returned, exactly matching the ones I could independently confirm
  had no active lease (cross-checked against the full tenant list as admin)

Then confirmed it in the actual UI dropdown as well.

## Related finding (not fixed as part of this bug)

While investigating this, it also became clear there's no confirmation step before a lease is
created, and no consent step from the tenant's side at all — a landlord could bind any tenant to
a lease with zero acknowledgment from them. That's a real product gap, but a separate piece of
work from this specific bug, so I tracked it separately rather than folding it in here.
