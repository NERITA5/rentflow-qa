# BUG-002: App crashes when selecting a unit before filling in lease dates

**Found:** During functional testing of the New Lease form, right after fixing BUG-001
**Environment:** Local dev (localhost:3000), Chrome, RentFlow
**Status:** Fixed and verified by me after applying the patch

## Summary

While testing the New Lease form as a landlord, picking a tenant and then a unit — before
touching the Start Date or End Date fields — crashed the whole page with an unhandled runtime
error. No graceful message, just a hard crash.

## Steps to reproduce

1. Log in as a landlord, go to Leases → New Lease
2. Select a tenant
3. Select a unit
4. Do **not** fill in Start Date or End Date yet

**Expected:** The form just sits there waiting for the remaining fields, same as it does before
you pick a tenant/unit.

**Actual:** Immediate crash — "Unhandled Runtime Error, RangeError: Invalid time value,"
pointing into `src/lib/utils.ts` at the `format` call inside `formatDate`.

**Severity:** Medium-High — doesn't lose data or expose anything sensitive, but it's a hard crash
on a core workflow (creating a lease), triggerable by a completely ordinary sequence of clicks
(nothing exotic about filling a form top-to-bottom).
**Priority:** High — blocks lease creation for a large share of realistic usage patterns
**Reproducibility:** 100%, every time, as long as dates are left empty when tenant+unit are set

## Root cause

The confirmation dialog that shows before a lease is created builds its summary text —
including formatted start/end dates — as a plain JavaScript expression inside the component's
render, not something that only runs once the dialog is actually opened. So the moment both a
tenant and a unit are selected, that expression runs immediately, even while the dialog is still
closed and the date fields are still empty strings. Trying to format an empty string as a date
produces an "Invalid Date," and the date-formatting function had no check for that — it just
handed the invalid value straight to `Intl.DateTimeFormat`, which throws instead of failing
quietly.

So really two separate mistakes stacked on top of each other: the summary text was being built
too early, and the formatter itself wasn't defensive enough to survive bad input if it ever
happened again elsewhere.

## The fix

Two changes:
1. The date-formatting functions now check if the date is valid before trying to format it, and
   return a placeholder ("—") instead of throwing if it isn't.
2. The confirmation dialog's summary text now also requires both dates to actually be filled in
   before it tries to build that string at all, not just a tenant and a unit.

## How I verified it

Repeated the exact steps that crashed it before — select tenant, select unit, no dates yet —
and confirmed the page no longer crashes. Then filled in the rest of the form and confirmed lease
creation still works end to end.

## Notes

This is a good example of a bug that isn't really about the specific date formatter — the deeper
lesson is that any value computed directly in a component's render (rather than deferred until
it's actually needed) will run on every render, even when the user hasn't gotten that far in the
form yet. Worth keeping an eye out for the same pattern elsewhere in the app.
